# Fin — Architecture

Fin is a single-target iOS SwiftUI app (`fin`, bundle id `dev.levischoen.fin`) that is an SSH terminal client plus a small local markdown reader/editor. This document traces every claim to the source in this repo as of the current tree.

## 1. Stack Overview

- **UI**: SwiftUI, one `WindowGroup` scene (`fin/finApp.swift`), forced `.preferredColorScheme(.dark)`.
- **Persistence**: SwiftData, deployment target **iOS 17.0** (set in both `project.yml`'s `options.deploymentTarget.iOS` and the `fin` target's own `deploymentTarget`). `SWIFT_VERSION` is pinned to `"5.0"`.
- **Terminal emulation**: [SwiftTerm](https://github.com/migueldeicaza/SwiftTerm) (MIT), pinned `from: 1.18.0`. Fin subclasses its UIKit `TerminalView` as `FinTerminalView`.
- **SSH transport**: [Citadel](https://github.com/orlandos-nl/Citadel) (`from: 0.12.1`), a pure-Swift, SwiftNIO-based SSH client — no libssh/OpenSSH shell-out. It supplies `SSHClient`, the PTY channel API (`withPTY`, `TTYStdinWriter`), and the OpenSSH-key-parsing initializers (`Curve25519.Signing.PrivateKey(sshEd25519:)`, `Insecure.RSA.PrivateKey(sshRsa:)`) used both for auth and for local key-import detection.
- Citadel's transport is layered on three more SPM packages declared in `project.yml`, each consumed by a *product* name that differs from its package name:
  - `SwiftNIOSSHFork` → product `NIOSSH`, from a fork (`https://github.com/Wellz26/swift-nio-ssh.git`, `from: 0.3.4`) rather than upstream swift-nio-ssh — Citadel depends on this patched fork.
  - `SwiftNIO` → product `NIO` (`from: 2.81.0`), Apple's async networking runtime underneath NIOSSH.
  - `SwiftCrypto` → product `Crypto` (`from: 3.12.3`), Apple's crypto primitives; `Curve25519.Signing.PrivateKey`/`Insecure.RSA.PrivateKey` are Crypto types Citadel extends with SSH-key parsing.
- **Project generation**: the Xcode project (`fin.xcodeproj`) is not hand-maintained — it's regenerated from `project.yml` by [XcodeGen](https://github.com/yonaskolb/XcodeGen) (`xcodegen generate`). Sources are picked up via a single glob (`sources: - path: fin`), so adding a file through Xcode's UI gets silently dropped on the next generate (per `.claude/skills/apple-build/SKILL.md`).
- Other `project.yml` facts worth noting: `DEVELOPMENT_TEAM: EC27UF79GL`, `CODE_SIGN_STYLE: Automatic`, `TARGETED_DEVICE_FAMILY: "1,2"` (iPhone+iPad), orientations locked to portrait + both landscapes on iPhone (all four on iPad), and an `NSLocalNetworkUsageDescription` ("Fin connects to SSH servers on your local network, including this Mac, over a direct TCP connection") — required because SSH-ing to a same-network host (e.g. the dev's own Mac) triggers iOS's local-network privacy prompt.

## 2. Data Model Layer

`FinApp.init()` builds one `ModelContainer` for exactly four `@Model` types: `Server.self, KeyMetadata.self, Clipping.self, MarkdownDocument.self` (`fin/finApp.swift:12`). Two other types that look like models are *not* SwiftData models:

- **`AppTheme`** (`fin/Models/AppTheme.swift`) is a plain `Codable, Equatable` struct (`backgroundHex`, `foregroundHex`, default `#000000`/`#00FF00` — classic green-on-black). It is never inserted into the model container; every consumer (`TerminalScreen`, `MarkdownReaderView`, `ThemeSettingsView`) independently declares its own `@AppStorage("themeBackgroundHex")` / `@AppStorage("themeForegroundHex")` and reconstructs `AppTheme` from those two raw hex strings. There is no shared observable theme object — the three call sites stay in sync only because they read/write the same `UserDefaults` keys.
- **`MarkdownFileDocument`** (`fin/Models/MarkdownFileDocument.swift`) is a `FileDocument`, not a SwiftData model. It exists purely to satisfy SwiftUI's `.fileExporter` generic constraint when creating a brand-new markdown file (see §10).

### `Server`
Fields: `id: UUID`, `name`, `host`, `port: Int` (default 22), `username`, `keyID: UUID?` (a *bare* UUID reference to `KeyMetadata.id` — not a SwiftData relationship, so it's resolved by hand), `tmuxSessionName` (default `"main"`), `connectCommand: String = ""` (empty by default — see §5), `createdAt: Date`.
Owned/queried by `RootView` (`@Query(sort: \Server.createdAt)`), `ServerListView` (same query, for the picker list), and mutated in place by `ServerEditView.save()`. `FinApp.init`'s `resolveCredentials` closure does the manual `keyID` → `KeyMetadata` join via a `FetchDescriptor<KeyMetadata>` predicate.

### `KeyMetadata`
Fields: `id: UUID`, `name`, `keyType: SSHKeyType` (`.ed25519`/`.rsa`, `String`-backed `Codable` enum), `importedAt: Date`. Stores **only metadata** — the private key bytes and passphrase never touch SwiftData; they live in `KeychainStore`, keyed by `KeyMetadata.id`. Queried by `ServerEditView` (`@Query(sort: \KeyMetadata.importedAt)`) to populate the key picker; created by `KeyImportView.save()`.

### `Clipping`
Fields: `id: UUID`, `name` (defaults to a Unix-timestamp string if none given), `text`, `direction: ClippingDirection` (`.to`/`.from`), `createdAt: Date`. Queried by `ClipboardManagerView` (`@Query(sort: \Clipping.createdAt, order: .reverse)`, filtered client-side by `direction`). Created two ways: manually in `AddClippingView` (always `.to`), or automatically by the terminal's clipboard-capture pipeline (`FinApp.init`'s `onCapturedClipping` closure inserts `Clipping(text:, direction: .from)` — see §6).

### `MarkdownDocument`
Fields: `id: UUID`, `name`, `bookmarkData: Data` (a security-scoped bookmark, not a path — see §9), `lastOpenedAt: Date`. Queried by `MarkdownListView` (`@Query(sort: \MarkdownDocument.lastOpenedAt, order: .reverse)`) and by `RootView` (unsorted `@Query`, matched by `id.uuidString` for the cross-mode resume target — see §11).

## 3. Session Layer

### `TerminalSession` — the state machine

`TerminalSession` (`fin/Session/TerminalSession.swift`) is `@MainActor final class ... ObservableObject, Identifiable`. Its `id` is the `serverID` passed at init. Two pieces of durable state matter beyond `SessionState`:

- `terminalView: FinTerminalView` — constructed exactly **once**, in `init`, and held for the object's entire lifetime. This is the anchor for instant resume (§4). `init` also builds a `KeyboardAccessoryRow` and wires it as `terminalView.inputAccessoryView` (§6), and wires `terminalView.onCopy` into the clipboard-capture pipeline.
- `generation: Int` — a private counter, starting at 0.

`SessionState` is `{ disconnected, connecting, connected, reconnecting }`.

**`connect(server:credentials:)`** only proceeds if `state == .disconnected || state == .reconnecting` (a guard that deliberately rejects calling `connect` again on an already-connecting/connected session). It sets `state = state == .reconnecting ? .reconnecting : .connecting` — i.e. a reconnect-triggered call keeps the UI showing "reconnecting" (yellow) rather than resetting to "connecting". It then **increments `generation`** and captures `myGeneration = generation` before doing anything async, cancels any in-flight `runTask`, and — if a previous `client` is still sitting around — fires off `Task { try? await staleClient.close() }` to close it without blocking. It then spins up a new `runTask` calling `run(server:credentials:generation:myGeneration)`.

**Why the generation counter exists.** `SSHClient.connect(...)` and `client.withPTY(...)` are both `async` and can take arbitrary wall-clock time (handshake, auth, channel open). Multiple `connect()` calls can legitimately overlap in time — e.g. the user backgrounds the app mid-handshake, the OS network path dies, they foreground again, and `RootView`'s `scenePhase == .active` handler calls `SessionManager.resumeActiveSessionIfNeeded`, which calls `connect()` a second time — all while the *first* `run()` task is still suspended somewhere (awaiting the handshake, or awaiting bytes on `inbound`). Without a monotonically increasing counter checked at every resumption point, the *first* (now-stale) task's eventual completion could stomp on state the *second*, valid attempt already established: assigning a dead `client` over the live one, or setting `state = .disconnected` right after the new attempt legitimately reached `.connected`. `run()` rechecks `myGeneration == generation` (or `== self.generation`) at **four** distinct points — immediately after the handshake returns (before adopting `client`), inside the `withPTY` setup closure (before touching `stdinWriter`/`state`), on every iteration of the `for try await chunk in inbound` loop (before feeding bytes into the terminal view), and in the post-loop cleanup (before nil-ing `client`/`stdinWriter`/resetting `state`). Because it's a counter (not a boolean "am I current" flag), a chain of three or more overlapping attempts still resolves correctly: only the single most-recent generation's writes ever land, and every older generation's unwind becomes a no-op.

**`disconnect()`** bumps `generation` (invalidating any outstanding `run()` task), cancels `runTask`, synchronously sets `state = .disconnected` and clears `client`/`stdinWriter`, then closes the SSH client asynchronously in a fire-and-forget `Task`.

**`markNeedsReconnect()`** only transitions `.connected → .reconnecting` (no-op otherwise). It's called by `SessionManager.resumeActiveSessionIfNeeded` immediately before `connect()`, specifically so `connect()`'s entry guard (`.disconnected || .reconnecting`) accepts the call even though the session's last known state was `.connected` — the app never explicitly disconnects when backgrounded, so on foreground the model can be stale (`state == .connected`) while the actual TCP socket is already dead.

`isConnected` is a separate, stricter signal than `state`: it reads `client?.isConnected ?? false` directly off the live `SSHClient`, rather than the cached state machine. `ServerListView`'s per-row status dot uses `isConnected` (so it only shows green while the socket is genuinely live), whereas `ControlStripView`'s status dot uses `state` (so it can distinguish yellow "connecting/reconnecting" from red "disconnected" — a distinction `isConnected` alone can't make).

### `SessionManager` — cache, credential resolution, last-active tracking

`SessionManager` (`fin/Session/SessionManager.swift`) is `@MainActor final class ... ObservableObject` holding:

- **`sessions: [UUID: TerminalSession]`** — the session cache, keyed by `Server.id`. `session(for:)` is a pure lookup-or-create; it never connects.
- **`resolveCredentials: (Server) -> ServerCredentials?`** — injected from `FinApp.init`. `SessionManager` has zero direct knowledge of SwiftData or Keychain; this closure is where `server.keyID` is joined against a `FetchDescriptor<KeyMetadata>` and `KeychainStore.loadPrivateKey`/`loadPassphrase`. Pure dependency injection keeps `SessionManager` free of persistence-layer imports.
- **`onCapturedClipping: (String) -> Void`** — also injected from `FinApp.init`; forwarded into every `TerminalSession` handed out by `session(for:)`.
- **`activeServerID: UUID?`** with a custom `didSet`: whenever set to non-nil (and *not* while `isRestoringFromStorage`), it writes **two** separate `UserDefaults` keys — `"lastActiveServerID"` (the UUID string, the plain "restore" path) and `"lastActiveServerTouchedAt"` (`Date().timeIntervalSince1970`, a distinct recency signal). Setting it to `nil` removes both. `isRestoringFromStorage` is a private flag toggled true only inside `init()` while re-hydrating the persisted `activeServerID` at cold launch — this exists specifically so that restoring the *old* server id on launch does **not** re-stamp `"now"` as its touched-at time. If it did, every cold launch would make the terminal side automatically win `RootView`'s recency comparison against the markdown side (§11), regardless of which was actually used more recently in the previous session, because "now" (launch time) always beats a stored past timestamp.

**`open(_:)`** sets `activeServerID = server.id` (triggering the stamp above), fetches/creates the session, and returns early without touching credentials if the session isn't `.disconnected` — i.e. it won't re-trigger a connect on something already connecting/connected/reconnecting. If `resolveCredentials` returns `nil` (no key attached, or key material unreadable from Keychain), it calls `session.reportMissingCredentials()` instead of connecting.

**`resumeActiveSessionIfNeeded(servers:)`** (called from `RootView` on `scenePhase == .active`) only acts when there's a cached session for `activeServerID`, and only when `!session.isConnected` **and** `state == .connected || state == .disconnected` — deliberately excluding `.connecting`/`.reconnecting` so it never interrupts an attempt already in flight. Because `TerminalSession` stores only a raw `serverID`, not a live `Server` reference, this method re-resolves the full `Server` model from the `servers` array passed in by `RootView`'s `@Query` before it can call `connect()` again.

**`close(_:)`** disconnects *and* removes the session from the cache entirely (unlike merely navigating away) — the `FinTerminalView`, its scrollback, and its SwiftTerm state are gone for good — and clears `activeServerID` if it was the closed server.

## 4. Instant Resume

`TerminalViewRepresentable` (`fin/Terminal/TerminalViewRepresentable.swift`) wraps a `TerminalSession`'s `FinTerminalView` in `UIViewRepresentable`. Its `makeUIView(context:)` **never constructs a new terminal view** — it applies the current theme and returns `session.terminalView` directly, the same `FinTerminalView` instance created once in `TerminalSession.init` and held for the session's full lifetime inside `SessionManager.sessions`.

This matters because SwiftUI can and does call `makeUIView` again whenever the representable's UIKit-side wrapper is torn down and rebuilt — e.g. `TerminalScreen` leaves the view hierarchy (opening the control strip's server-list sheet, or backgrounding) and comes back. Each such call still hands back the exact same object reference (`session` is the same `TerminalSession` retrieved from `sessionManager.sessions[server.id]`, not a fresh one), so UIKit's job reduces to reparenting an existing `UIView`/`CALayer` into a new superview — a layer-tree move, not a rebuild. The view already carries SwiftTerm's live in-memory scrollback buffer, cursor position, and PTY dimensions, so nothing needs to be replayed or re-rendered, and no new SSH handshake happens. Compare to constructing a fresh `SwiftTerm.TerminalView` per appearance: it would come up blank, since SwiftTerm doesn't persist scrollback outside that in-memory buffer object.

`TerminalScreen.body` (`fin/Views/TerminalScreen.swift`) is built to exploit this: `if let session = sessionManager.sessions[server.id]` is a synchronous, side-effect-free dictionary lookup performed during `body` evaluation itself (the comment above it: "renders instantly on this very first evaluation with no side effect"). Only the `else` branch — a session that's never been opened this launch — defers the side-effecting `sessionManager.open(server)` call into a `.task`, so it never runs during declarative `body` evaluation. Resuming an already-open session therefore renders the same `FinTerminalView` the instant `TerminalScreen` appears, with no async gap.

## 5. Why SSH+tmux, Not Real Mosh

The `NSLocalNetworkUsageDescription` string in `project.yml` says it plainly: "Fin connects to SSH servers on your local network... over a direct TCP connection." `TerminalSession.run()` calls `SSHClient.connect(...)` — ordinary SSH over TCP via Citadel/NIOSSH, not mosh's own UDP-based State Synchronization Protocol (SSP).

Real mosh's defining properties — roaming across network changes (WiFi↔cellular) without dropping the session, and local echo/prediction that keeps typing responsive over high-latency/lossy links — require a custom UDP wire protocol and a `mosh-server` companion binary running (and reachable through firewalls/NAT on a UDP port) on every server you connect to. Nothing in this app's dependency graph (Citadel, NIOSSH, SwiftNIO, swift-crypto) implements that protocol, and there's no mature pure-Swift SPM package that does.

Instead, Fin approximates mosh's user-facing benefit — "reconnect and land back in the shell state you left, not a blank one" — with ordinary SSH plus a server-side multiplexer: `Server.connectCommand` (`fin/Models/Server.swift`) is sent verbatim right after the shell connects, and `ServerEditView` offers a one-tap default of `exec tmux new-session -A -s <tmuxSessionName>` (a button in its "Advanced" `DisclosureGroup`, disabled while the tmux session-name field is empty, that overwrites `connectCommand` with that exact string interpolated with the current `tmuxSessionName`). Because tmux keeps the real shell process and its scrollback alive independent of the SSH TCP connection, when `TerminalSession`'s reconnect path (`markNeedsReconnect` → `connect()`, §3) re-establishes the socket, `connectCommand` reattaches to the *same* running tmux session rather than starting a fresh shell.

The actual engineering tradeoff this buys, versus real mosh:
- **It's opt-in, not automatic.** `connectCommand` defaults to `""` — nothing is sent unless the user configures it (the doc comment on the field explains the empty default is deliberate, for hosts that already auto-attach via a shell-profile). Forgetting to set it, or not having tmux installed server-side, just gets you a plain new shell on reconnect.
- **No mid-connection roaming.** The TCP socket still fully drops on a network change; "resume" here means *detect-then-reconnect-then-reattach* — a visible gap with a fresh handshake and auth round-trip — not mosh's seamless in-flight continuation.
- **No local echo/prediction.** Every keystroke still round-trips over the live SSH connection at full latency; on a bad link, typing feels exactly as laggy as plain SSH, because it *is* plain SSH.

In short: SSH+tmux gets "reconnect resumes your shell" cheaply by pushing state-durability onto a server-side multiplexer, at the cost of mosh's actual wire-level resilience and interactivity — which this dependency stack has no way to provide anyway.

## 6. Terminal Input Layer

### `FinTerminalView` — copy capture and Ctrl-arming

`FinTerminalView` (`fin/Terminal/FinTerminalView.swift`) subclasses `SwiftTerm.TerminalView` and overrides two things:

**`copy(_ sender:)`** captures `getSelection()` *before* calling `super.copy(sender)` (which performs UIKit's normal copy-to-`UIPasteboard`), then — if non-empty — invokes `onCopy?(text)`. `TerminalSession.init` wires `terminalView.onCopy` to `captureCopiedText(text, alsoWriteToPasteboard: false)` (pasteboard write already happened via `super.copy`). Separately, the `TerminalViewDelegate.clipboardCopy(source:content:)` callback fires when the *remote* side emits an OSC 52 clipboard-set escape sequence — since that path isn't triggered by a UIKit copy gesture, it calls `captureCopiedText(text, alsoWriteToPasteboard: true)` to write the pasteboard itself. Both paths converge on `captureCopiedText`, which calls `onCapturedClipping(text)` — wired all the way back to `FinApp.init`'s closure that inserts `Clipping(text:, direction: .from)`. So *every* copy — a manual local selection-copy or a remote OSC-52 push — is automatically logged as a `.from` `Clipping` row, visible later in `ClipboardManagerView`'s "From" tab. That's the "clipboard-capture pipeline."

**`ctrlArmed: Bool`** and the override of **`insertText(_:)`**: when armed, the very next inserted character is intercepted — `controlCode(for:)` first uppercases the character (so tapping an unshifted on-screen key, which normally inserts lowercase, still works — `"c"` and `"C"` both resolve the same way) and, if the uppercased value lands in ASCII range `64...95` (`@`, `A`–`Z`, `[`, `\`, `]`, `^`, `_`), maps it to `byte - 64` (e.g. `"c"`/`"C"` → `0x03`, Ctrl-C) and sends that single byte via `terminalDelegate?.send(source:data:)`, bypassing normal text insertion entirely; then immediately disarms (`ctrlArmed = false`), making it a one-shot per tap rather than a held modifier. Anything that isn't a single recognized character falls back to `super.insertText(text)` (still disarming first). This exists because the on-screen keyboard has no physical Ctrl key.

### `KeyboardAccessoryRow`

`KeyboardAccessoryRow` (`fin/Terminal/KeyboardAccessoryRow.swift`) is a `UIView` installed as `terminalView.inputAccessoryView` (wired in `TerminalSession.init`) — it sits directly above the software keyboard. It's a horizontal `UIStackView` of buttons: **Ctrl**, **Esc** (`0x1B`), **Tab** (`0x09`), and the four arrow keys (`ESC [ D/B/A/C`). The Ctrl button's action calls `onToggleCtrl` — which `TerminalSession.init` wires to `terminalView.ctrlArmed.toggle()`, returning the new value so the button can restyle itself (white-tinted background while armed). The other keys call `onSendBytes` directly with their fixed byte sequence — they bypass `insertText`/Ctrl-arming entirely, going straight through `TerminalSession.send(bytes:)`.

## 7. Control Strip and Its Overflow Menu

`ControlStripView` (`fin/Views/ControlStripView.swift`) is the persistent header bar `TerminalScreen` places above `TerminalViewRepresentable` — always visible while a terminal session is on screen. It's a single `HStack(spacing: 18)`: a status dot (`color(for: session.state)`: green `.connected`, yellow `.connecting`/`.reconnecting`, red `.disconnected`), the server's name (monospaced footnote, `lineLimit(1)`), a `Spacer()`, and five trailing controls in a flat row — four SF Symbol buttons followed by a `Menu`.

**The four buttons, in order:** `xmark.circle` (red; calls `sessionManager.close(server.id)`, deliberately left tappable in every session state, including mid-connect/reconnect — the in-code comment: *"Always tappable — including mid-connect/reconnect — so a hung or wrong connection attempt is never a dead end."*), `server.rack` (opens a `.sheet` presenting `HomeView()` — the server switcher), `doc.on.clipboard` (opens a `.sheet` presenting `ClipboardManagerView(session:)`), and `paintpalette` (opens a `.sheet` presenting `ThemeSettingsView()`).

**The trailing `Menu`** (labeled with `line.3.horizontal`) holds the two navigation actions that don't get their own icon buttons: **Page Up** and **Page Down**, each calling `session.send(text:)` directly with a raw terminal escape sequence rather than any byte-array/keyboard-accessory path — Page Up sends `"\u{1B}[5~"` (`ESC [ 5 ~`) and Page Down sends `"\u{1B}[6~"` (`ESC [ 6 ~`), the standard xterm CSI sequences for those keys.

This is a plain SwiftUI `Menu`, not a paging control — there is no `ScrollView`, no `TabView(.page)`, and no swipe gesture anywhere in this view. The in-code comment spells out why: *"A menu instead of a swipe-to-reveal second page — the swipe gesture proved unreliable when constrained to this small strip."* An earlier paging-strip design (swiping between a primary and secondary row of buttons within a fixed-width region) was tried and dropped in favor of this tap-to-reveal `Menu`, specifically because the swipe gesture didn't work reliably at this small, embedded (not full-screen) size.

## 8. Other Screens and Navigation

- **`HomeView`** (`fin/Views/HomeView.swift`) is a `NavigationStack` wrapping a segmented `Picker` (`Mode`: `.terminal` / `.markdown`) that swaps between `ServerListView` and `MarkdownListView` beneath it, with a navigation title that tracks the picked mode ("Servers" / "Markdown"). It's the `.home` case of `RootView`'s `Route`, and it's also what `ControlStripView`'s server-switcher button presents as a `.sheet` over an active terminal session.
- **`ServerListView`** (`fin/Views/ServerListView.swift`) lists all `Server`s (`@Query(sort: \Server.createdAt)`), each row a tappable connect button (`sessionManager.open(server)` then `dismiss()`) plus a separate pencil-circle button that opens `ServerEditView` in a `.sheet(item:)`. A per-row status dot uses `session.isConnected` (green) vs. gray — not `state`, so it only lights up once the SSH client is genuinely live. Swipe-to-delete calls `sessionManager.close(server.id)` before `modelContext.delete(server)`, so a deleted server's live session (if any) is torn down rather than orphaned in the cache. The "+" toolbar button opens `ServerEditView(server: nil)` for a new server.
- **`ServerEditView`** (`fin/Views/ServerEditView.swift`) is a `Form` for name/host/port/username, a private-key `Picker` (`@Query(sort: \KeyMetadata.importedAt)`, `"None"` plus every imported key) with an "Import Key from Files…" button that presents `KeyImportView` in a `.sheet` (its completion closure sets `selectedKeyID`), and a collapsed-by-default `DisclosureGroup("Advanced")` holding the tmux-session-name field, the free-text `connectCommand` field (with the "leave blank for a plain shell" caption quoted in §5), and the one-tap `exec tmux new-session -A -s <name>` quick-fill button. `save()` either mutates the passed-in `Server` in place or constructs and inserts a new one; the confirmation button is disabled until name/host/username are all non-empty.
- **`KeyImportView`** — see §9 (Security) for the parsing/detection logic; it's presented from `ServerEditView`'s "Import Key" button.
- **`ClipboardManagerView`** (`fin/Views/ClipboardManagerView.swift`) is a segmented "To"/"From" `Picker` over `@Query(sort: \Clipping.createdAt, order: .reverse)`, filtered client-side by `direction`. Tapping *any* listed clipping — in either tab — calls `session.send(text:)` then `dismiss()`, pasting it straight into the live terminal; the row's tap target and swipe-to-delete are identical in both tabs. Only the "+" toolbar button is direction-specific: it's shown on the "To" tab only, opening the private `AddClippingView` sheet (a name field defaulting to a Unix-timestamp string, plus a `TextEditor`, inserting a `Clipping(direction: .to)`). "From" entries have no manual-add path — they're populated solely by the clipboard-capture pipeline (§6) — but are otherwise tappable-to-paste and swipe-to-delete exactly like "To" entries.
- **`ThemeSettingsView`** (`fin/Views/ThemeSettingsView.swift`) is a two-`ColorPicker` `Form` (Background, Text) bound through computed `Binding<Color>` properties that convert to/from the `@AppStorage` hex strings via `Color(hex:)`/`toHexString()`, plus a "Reset to Classic Green on Black" button that restores `AppTheme.default`'s two hex values. It's presented as a `.sheet` from both `ControlStripView` (over the terminal) and `MarkdownReaderView`'s toolbar (over the markdown reader) — the same view, same `@AppStorage` keys, so a change made from either surface is visible in both immediately.

## 9. Security

### `KeychainStore`

`KeychainStore` (`fin/Persistence/KeychainStore.swift`) is a stateless enum namespace over two Keychain "services" — `dev.levischoen.fin.privatekey` and `dev.levischoen.fin.passphrase` — with `kSecClassGenericPassword` items keyed by `account = keyID.uuidString`. That's the *only* link between a `KeyMetadata` row and its Keychain material — a matching UUID string, not a formal relationship. Items are saved with `kSecAttrAccessible: kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (device-only, excluded from iCloud Keychain sync/backup, accessible only while unlocked). `save()` always calls `delete()` first, so re-saving under an existing account overwrites cleanly instead of failing on a duplicate-item add. `load*` calls return `nil` silently on any failure (no error surfaced) — a corrupted/missing item just looks like "no key". `deleteKeyMaterial(for:)` removes both service entries.

### Private key import — OpenSSH format only

`KeyImportView.attemptParse()` (`fin/Views/KeyImportView.swift`) tries exactly two initializers, in order: `Curve25519.Signing.PrivateKey(sshEd25519: pemString, decryptionKey:)`, then `Insecure.RSA.PrivateKey(sshRsa: pemString, decryptionKey:)` — both Citadel/swift-crypto initializers that parse OpenSSH's own armored private-key format (`-----BEGIN OPENSSH PRIVATE KEY-----`), not classic PKCS#1/PKCS#8 PEM. Key type isn't user-selected; it's inferred entirely by which initializer succeeds. Since those are the *only* two parse attempts made anywhere in the app, any other format — traditional PEM RSA, ECDSA, DSA, or a non-OpenSSH-armored key — fails both and surfaces the literal message: *"Couldn't read this key. Only OpenSSH-format ed25519/RSA keys are supported — check the passphrase, or the key format."* Passphrase-protected keys are handled by re-running the same `attemptParse()` with `Data(passphrase.utf8)` as `decryptionKey` (the "Retry with Passphrase" button). The file itself is picked via `.fileImporter(allowedContentTypes: [.item])` (any file type) and read with a security-scoped access bracket (`startAccessingSecurityScopedResource()`/`stopAccessingSecurityScopedResource()`) that's released immediately after reading — unlike markdown files (§10), imported key files don't need a persisted bookmark, since only the decoded key bytes (not the file itself) are kept, in Keychain. On save, the private key always goes to Keychain; the passphrase is only saved if non-empty — an empty passphrase means no Keychain item exists for it at all, and `resolveCredentials` (in `FinApp.init`) treats a `nil` load the same as "no passphrase."

### Host key validation

Worth flagging as a real, load-bearing fact rather than an oversight to guess at: `TerminalSession.run()` connects with `hostKeyValidator: .acceptAnything()` — host keys are accepted unconditionally, with no TOFU (trust-on-first-use) pinning or verification against previously seen keys.

### Security-scoped bookmarks for markdown files

`MarkdownDocument.bookmarkData` is the *only* thing persisted about a markdown file's location — never a raw path. Both `MarkdownListView.handlePicked` (open) and `handleCreated` (create) call `url.bookmarkData()` while the picker-granted access is still active (`startAccessingSecurityScopedResource()` ... `defer { stopAccessingSecurityScopedResource() }`) and store the result. Every later access — `MarkdownReaderView.load()` and `.save()` — independently re-resolves via `URL(resolvingBookmarkData:bookmarkDataIsStale:)` and re-brackets its own start/stop access-scope pair (the import-time scope is long gone by then). Resolution failure surfaces as *"This file's location can no longer be resolved. It may have moved."* — a reachable state if the user moves/deletes/renames the file from outside the app. `isStale` is read into but never acted on — a stale-but-resolvable bookmark is treated as fine, with no refresh-on-staleness logic.

## 10. Markdown Subsystem

### Open vs. create

`MarkdownListView`'s "+" menu offers two paths, both ending in a `MarkdownDocument` insert:

- **Open Existing File…** → `.fileImporter(allowedContentTypes: [.item])` (any file type — not restricted to text/markdown UTTypes) → `handlePicked(_:)`. Before inserting, `sameFile(_:as:)` resolves each existing `MarkdownDocument`'s bookmark and compares `resolved.path == url.path`; a match just bumps that document's `lastOpenedAt = Date()` instead of creating a duplicate row. Otherwise it inserts `MarkdownDocument(name: url.lastPathComponent, bookmarkData:)`.
- **New File** → `.fileExporter(document: MarkdownFileDocument(), contentType: .plainText, defaultFilename: "Untitled")` → `handleCreated(_:)`. `MarkdownFileDocument()` (no args) starts with empty `text`, so the OS save-location picker creates a blank file. `handleCreated` does the same bookmark-capture-and-insert as `handlePicked` (no dedup check needed — it's necessarily new), then sets `newlyCreatedDocument = document`, which drives a `.sheet(item:)` presentation of `MarkdownReaderView(document:startInEditMode: true)` — creating a file drops you straight into editing it, not back at the list.

Both failure paths (`.fileImporter`/`.fileExporter` returning `.failure`, or the `try url.bookmarkData()` call throwing) surface through the same `importErrorMessage` state, driving one shared `.alert("Couldn't Open File")`.

### Edit-mode save-back-to-disk flow

`MarkdownReaderView` (`fin/Views/MarkdownReaderView.swift`) takes an `isRoot` flag (true only when `RootView` places it directly as the app's resume route — see §11) and a `startInEditMode` flag (true only for the just-created-file sheet from `MarkdownListView`, initializing `isEditing` accordingly). It toggles `isEditing` via the pencil/checkmark toolbar button; while `true`, `body` swaps the read-only `Text(content)` for a plain `TextEditor(text: $rawText)` (styled with the same `@AppStorage`-backed theme colors as the read-mode view, via `.scrollContentBackground(.hidden)` plus explicit background/foreground). `load()` (fired once via `.task`) resolves the bookmark, reads the file, stamps `document.lastOpenedAt = Date()` (a SwiftData mutation with no explicit `modelContext.save()` — relies on SwiftData's autosave), populates `rawText`, and separately builds the read-mode `content: AttributedString?` via `render(text)`, which uses `AttributedString(markdown:options:)` with `interpretedSyntax: .inlineOnlyPreservingWhitespace` — inline constructs (emphasis, links, code spans) are rendered, block structure and whitespace are preserved as-typed — falling back to a plain, un-styled `AttributedString(text)` if parsing throws.

`save()` mirrors `load()`'s resolve/scope pattern, then encodes via a safely-guarded `rawText.data(using: .utf8)` — not a force-unwrap; a `nil` here (practically unreachable for a `String`, but still guarded) surfaces as `"Couldn't encode the edited text."` rather than crashing — and does a full overwrite with `Data.write(to:)` (not an atomic-replace) — no partial-write protection beyond whatever `Data.write` itself guarantees. On success it also calls `render(rawText)` so flipping back to read-mode shows the edit immediately without a re-read from disk; on a `Data.write` failure, the `catch` sets `saveError`, driving an alert with `error.localizedDescription`. `save()` is called from three places: the checkmark toolbar button, the "back to list" button (`isRoot` only, if still editing — which also flips `isEditing = false` afterward), and `.onDisappear` — an explicit safety net (per the code comment) for a back-swipe/back-button dismissal that skips both toolbar buttons, so an edit is never silently lost.

## 11. Cross-Mode Resume Logic (`RootView`)

`RootView` (`fin/Views/RootView.swift`) computes a private `Route` enum — `.terminal(Server) | .markdown(MarkdownDocument) | .home` — from two independently-tracked "last touched" signals:

- **Terminal side**: `sessionManager.activeServerID` (live, in-memory `SessionManager` state — though its *initial* value at cold launch comes from `SessionManager.init` reading `UserDefaults["lastActiveServerID"]`), matched against the `@Query`'d `servers` array.
- **Markdown side**: `@AppStorage("lastActiveMarkdownDocumentID") private var lastActiveMarkdownDocumentID: String = ""`, read directly in `RootView` — *not* proxied through any manager object, unlike the terminal side — matched against `@Query`'d `markdownDocuments` by `id.uuidString`.

The route is a 4-way switch on `(terminalTarget, markdownTarget)`: neither present → `.home`; only one present → that one; **both present** → compare two `@AppStorage` `Double` (Unix-timestamp) values, `lastActiveServerTouchedAt >= lastActiveMarkdownTouchedAt` — terminal wins ties and wins whenever its stamp is at least as recent. `RootView` also observes `scenePhase`: on transition to `.active` it calls `sessionManager.resumeActiveSessionIfNeeded(servers:)` (§3), independent of routing.

**The actual gating condition that stops a sheet-peek from hijacking the resume target** lives upstream of `RootView`, in what's allowed to *write* the markdown timestamp at all: `MarkdownReaderView.load()` only stamps `lastActiveMarkdownDocumentID`/`lastActiveMarkdownTouchedAt` `if sessionManager.activeServerID == nil`. Since `ControlStripView` presents `HomeView` (and from there, markdown) via `.sheet` while a terminal session is still the live route underneath, a user peeking at a markdown file from that sheet does **not** touch the markdown touched-at at all — because `activeServerID` is still non-nil at that moment — so the peek can never win the recency comparison against the terminal session that's still genuinely active. There's no symmetric guard on the terminal side (`SessionManager.activeServerID`'s `didSet` stamps unconditionally, modulo only the launch-restore guard from §3) because opening/switching to a server is always meant to become the resume target — it's specifically the markdown-reachable-without-leaving-the-terminal-route path that needed the extra condition.

One more explicit clear: the "back to list" button in `MarkdownReaderView` (`isRoot` only) removes both `lastActiveMarkdownDocumentID` and `lastActiveMarkdownTouchedAt` from `UserDefaults` outright — deliberately backing out of markdown-as-root clears the markdown resume target entirely, rather than just leaving it to be outraced by a fresher terminal touch later.

## 12. Build, Signing, and Deploy Tooling

### XcodeGen regeneration

`fin.xcodeproj` is generated output, not source of truth — `project.yml` is. `scripts/deploy-iphone.sh` runs `xcodegen generate` as its first real step, so every deploy regenerates the project fresh. `.claude/skills/apple-build/SKILL.md` warns explicitly against adding files via the Xcode UI, since the `sources: - path: fin` glob-based regeneration would drop them on the next `generate`.

### Two distinct signing gotchas (from `apple-build/SKILL.md`)

**1. Wrong/orphaned team ID.** `project.yml` hardcodes `DEVELOPMENT_TEAM: EC27UF79GL` with `CODE_SIGN_STYLE: Automatic`. `security find-identity -v -p codesigning` can list *more* certs than are actually usable — this Mac has an orphaned `Apple Development: Levi Schoen (J8CNP2QBGB)` cert in the keychain with no corresponding signed-in Xcode account. A cert existing in Keychain does not mean its team ID works for automatic signing. If `DEVELOPMENT_TEAM` points at a team Xcode doesn't recognize as signed-in, `-allowProvisioningUpdates` fails with `No Accounts: Add a new account...` / `No profiles for '<bundle id>' were found` — which *reads* like "no Apple ID is signed into Xcode at all" but usually isn't. The real diagnostic is `defaults read com.apple.dt.Xcode IDEProvisioningTeamByIdentifier` (the actual source of truth for which team(s) Xcode has signed-in accounts for); the fix is pointing `DEVELOPMENT_TEAM` at a team ID actually present in that list — not a GUI sign-in step. A genuine "nobody's signed in" case shows an *empty* `IDEProvisioningTeamByIdentifier`, and only then is the one-time GUI step (Xcode → Settings → Accounts → **+**, requiring Apple ID + 2FA) actually necessary — and it can't be done headlessly.

**2. `errSecInternalComponent` keychain-ACL issue.** A separate, unrelated failure: `codesign` throws `errSecInternalComponent` when the signing process isn't running in the GUI (Aqua) login session — verified via `launchctl managername` (expect `Aqua`) or that `screencapture -x` succeeds. This is exactly why `scripts/deploy-iphone.sh` is a real shell script meant to be invoked from an Aqua-session shell (Claude Code's `!` prefix, or a real Terminal window) rather than as an inline command from a detached/background process — its own header comment says so directly. If it still happens from a confirmed-Aqua shell, the documented fix is Keychain Access → the **Apple Development** private key → Get Info → Access Control → **Allow all applications** (a permission on the signing key itself, not a code/config issue).

Simulator builds sidestep both gotchas via `CODE_SIGNING_ALLOWED=NO` (no signing attempted).

### `scripts/deploy-iphone.sh` flow

1. `set -euo pipefail`; pins `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`; `cd` to repo root.
2. Device UDID is hardcoded (`DEV=59C072A6-6201-5A10-AA86-4EE176FDC8A8`) — re-derive via `xcrun devicectl list devices` if it changes.
3. Checks `which xcodegen` (exits with an install hint if missing), then `xcodegen generate`.
4. `rm -rf` the expected product path (`build-device/Build/Products/Debug-iphoneos/fin.app`) **before** building — the comment explains this guarantees a failed build can never fall through to installing a stale product from a previous run; success is gated on the build's own exit code, not merely on the product existing afterward.
5. Runs `xcodebuild ... -configuration Debug -allowProvisioningUpdates build`, piped through `grep -iE "error:|BUILD SUCCEEDED|BUILD FAILED|CodeSign failed"` for a readable log — but wrapped in `set +o pipefail` / `set -o pipefail` specifically so grep's own exit code (1, on a quiet log with no matches) can't be mistaken for xcodebuild's; the real status is captured via `PIPESTATUS[0]` immediately after the pipeline.
6. Exits without installing if the build's exit code was non-zero, or if the app bundle still doesn't exist despite a reported success.
7. `xcrun devicectl device install app --device "$DEV" "$APP"`, then `xcrun devicectl device process launch --device "$DEV" dev.levischoen.fin`.
